## S1 Gennari, Neal, Galdzicki, Cook 2011 — Multiple ontologies in action: composite annotations for biosimulation models

- J Biomed Inform 2011;44(1):146-154. DOI [10.1016/j.jbi.2010.06.007](https://doi.org/10.1016/j.jbi.2010.06.007). PMID 20601121, PMCID PMC2989341 (author manuscript).
- Access: full text read (PubMed/PMC author manuscript). Europe PMC `fullTextXML` returned HTTP 500 (consistent with the user's earlier attempt). Copyright: "Copyright © 2010 Elsevier Inc. All rights reserved." Not redistributed; quotations only.
- Version: published article 2011; author manuscript in PMC. No supplement, model or code noted in the text; the demonstration models are JSim MML models (CV, BARO, VSM) from the authors' 2008 work.

Quotations

1. [1.1 Reference ontologies for biology] "Modelers use variables that represent physical properties of physical entities that change over time; for example, the pressure of aortic blood". → Q1, Q2.
2. [1.1] "To annotate this variable, there are (at least) three relevant classes: fluid pressure, the aorta (where pressure is measured) and the blood in the aorta." → Q1.
3. [1.1] "blood exists in many spatial compartments (arteries, veins, chambers of the heart, etc), and for each there is a pressure, a volume, and a net flow rate—should any single ontology … enumerate all such possibilities?" → Q1 (post-coordination argument).
4. [2. Composite annotations] "For biosimulation variables, each composite annotation must include exactly one physical property reference, and must contain at least one physical entity reference. More precisely, the first physical entity must be the one which possesses the property being measured." → Q1, Q3 (grammar).
5. [2] "for any fluid flow-rate annotation, the initial physical entity must be a bodily substance (defined by the FMA as a fluid)." → Q3 (constraint on allowed annotations).
6. [2] "if terms in an annotation lack links to ontologies, then these terms cannot be merged or recognized in any automatic manner." → Q3, Q4.
7. [4. Demonstration] "The SemGen merger tool … provides a set of 'suggested' merges where the semantics are similar or identical, and … allows the user to create manual connections between any two variables". → Q2, Q3.
8. [4] "To correctly merge the models, the user must choose to make equivalent two variables across these models: 'Resistance of systemic arteries and capillaries' from CV+BARO and 'Resistance of systemic arterioles' from VSM. This choice is an example of how the model merging process will remain only semi-automatic—individual researchers must make subjective decisions about when and where it is appropriate to link models." → Q3 (human-decided equivalence).
9. [4] "we found that the semi-automatically merged system generated by SemGen reproduced the numerical results of the original hand-merged model". → Q4 (numeric check after merge).
10. [5.1 Knowledge sharing] "The composite annotation schema we have described is for model variables, and is not sufficient for annotating the model equations that capture mathematical relationships between variables." → Q2 (equivalence annotation ≠ dependency annotation).
11. [5.1] "a critical aspect to capture is which model variables play which roles in a particular equation." → Q2.
12. [5.2 Semantic web technologies] "our current tool only suggests exact semantic matches, where all parts of the composite annotation match." → Q3.
13. [5.2] "if the property selected is 'fluid pressure' (from the OPB), then we could use inference to only allow for the selection of a physical entity that is a bodily fluid." → Q3 (constraint idea, stated as future work).
14. [1.2] "Models frequently have serious errors of unitary imbalance, mathematical inconsistency, and syntax." → Q4.

Author claim / our interpretation / independent confirmation

- Claim: a composite annotation (one OPB property + ordered physical entities linked by RO relations) disambiguates variables that a single term cannot, and exact-match comparison of such annotations supports merging.
- Our reading: the paper itself says equivalence suggestions are exact matches only and that equations/roles are out of scope of the variable annotation; "same thing" and "depends on" are therefore different layers by the authors' own account. Reference points (gauge versus transmural) and temporal meaning (instantaneous versus beat-mean) are not part of the stated grammar.
- Independent confirmation: the exact-match behaviour and the role concept are confirmed in Cook 2013 (S2, dependency "player" roles) and in the 2019 SemGen note (S5, overlap listed for user choice). The constraint that a flow-rate's first entity be a fluid was checked against the SemSim annotation of the Smith model (S9): every Q_* annotation starts from "Portion of blood" (fma9670).
- Limits/unknowns: no evaluation with users ("has not yet been formally evaluated with users"); no statement on reference points or units in the grammar; demonstration is JSim only.

## S2 Cook, Neal, Bookstein, Gennari 2013 — Ontology of physics for biology: representing physical dependencies as a basis for biological processes

- J Biomed Semantics 2013;4:41. DOI [10.1186/2041-1480-4-41](https://doi.org/10.1186/2041-1480-4-41). PMID 24295137, PMCID PMC3904761.
- Access: full text read (PubMed/PMC) and Europe PMC XML retained as `docs/evidence/d_fulltext_PMC3904761_cook2013_opb.xml`. Licence: "Copyright © 2013 Cook et al.; licensee BioMed Central Ltd." CC BY 2.0 (PMC record).
- Version: OPB described as OWL, "available from BioPortal". The retained OWL files are v1.07 (SemGen bundle) and GitHub master 2022-12-16; see S10.

Quotations (the PMC text drops the OPB class names that were typeset as links; gaps are shown as "…")

1. [Background and aims] "if we annotate only physical properties of participating entities (e.g., things such as hearts and portions of blood), then we ignore the dependencies amongst property values (e.g., physical laws and axioms) by which physical processes occur." → Q2.
2. [Background and aims] "We extend our prior work in semantic annotation to not only annotate model variables but also computations amongst variables (i.e. the equations) against OPB:…classes that semantically represent the meaning of the computations". → Q2.
3. [Background and aims] "a model that simulates blood flow will, typically, calculate the dependence of blood flow rates … on blood pressure differentials … along flow paths using, in the simplest case, a fluid analogue of Ohm's law … Similarly, that model will typically calculate blood pressures as functions of the volumes of blood in a vessels according to fluid analogues of Hooke's law". → Q2 (resistive and capacitive dependencies; matches E27/E28 and E19-E25 of the Smith model).
4. [Physical dependencies represent physical laws] "a dependency representing Ohm's law would have as property players a current (I), a voltage differential (E), and a resistance (R). Just as process participants must be distinguished according to their participatory role …, players and their roles in dependencies are related by OPB:…object relations." → Q2 (roles).
5. [Boundary dependencies] "the change in amount of 'stuff' (e.g., volume of blood …) in an entity changes over a span of time as the temporal integral of the flow rate of stuff". → Q2 (matches the volume ODEs E9, E15, E20, E22, E24, E26).
6. [Rate dependencies] "OPB:…represent how elements that behave as analogues of electrical inductors store kinetic energy. For example, OPB:…represents the dependency of the momentum of a moving portion of fluid on the fluid pressures that move the fluid". → Q2 (matches the valve inertance ODEs E29-E32).
7. [Constitutive properties of rate dependencies] "the resistive flow dependency that relates fluid volume flow-rate to input pressure of a vascular blood flow process is particularly non-linear … Representing such complexities in broad and complete form is currently beyond the scope of the OPB". → Q3, Q4 (scope limit; piecewise valve laws are not covered).
8. [OPB current limitations, next steps] "A next step is to implement…relations for dependencies … that link property instances of physical entities according to the particular mathematical role they play the dependency computation. For example, calculating fluid flow-rate from a portion-of-fluid-A to portion-of-fluid-B holds only for the fluid pressure of A, the fluid pressure of B, and the fluid flow resistance from A-to-B; other pressures and resistances are irrelevant." → Q2, Q3 (direction and role binding were still future work in 2013).
9. [Discussion] "OPB:…maps to PATO:…in the Phenotype Ontology". → Q3 (cross-ontology overlap exists; not an identity claim for our terms).

Author claim / our interpretation / independent confirmation

- Claim: physical laws can be classified as OPB dependency classes with role-bound property players, separating "what a variable is" from "how its value depends on others".
- Our reading: this is the published basis for keeping equivalence (composite annotation of a variable) apart from dependency (OPB dependency class with players). The paper states that instance-level role binding was not yet implemented, so the ontology alone does not say which pressure drives which flow; the model equations do.
- Independent confirmation: the retained OPB master OWL contains the named classes with definitions (S10): Resistive flow dependency OPB_01572, Fluid capacitive dependency OPB_01543, Fluid inductive dependency OPB_01541, Temporal integrative dependency OPB_01173. Whether these classes carry formal player restrictions was not checked (would need an OWL reasoner pass; not done).
- Limits/unknowns: OWL description-logic implementation "far from complete" (authors); non-proportional dependencies out of scope; our mapping of Smith equations to these classes is a proposal, not an entailment.

## S3 Neal, König, Nickerson, Mısırlı, Kalbasi, Dräger, Atalag, Chelliah, Cooling, Cook, Crook, de Alba, Friedman, Garny, Gennari, Gleeson, Golebiewski, Hucka, Juty, Myers, Olivier, Sauro, Scharm, Snoep, Touré, Wipat, Wolkenhauer, Waltemath 2019 — Harmonizing semantic annotations for computational models in biology

- Brief Bioinform 2019;20(2):540-550. DOI [10.1093/bib/bby087](https://doi.org/10.1093/bib/bby087). PMID 30462164, PMCID PMC6433895.
- Access: full text read (PubMed/PMC); Europe PMC XML retained as `docs/evidence/d_fulltext_PMC6433895_neal2019_harmonizing.xml`. Licence: the retained JATS XML carries the licence element "https://creativecommons.org/licenses/by/4.0/ … This is an Open Access article distributed under the terms of the Creative Commons Attribution License" (CC BY 4.0); the PubMed record shows only "© The Author(s) 2018. Published by Oxford University Press."
- Supplements: two example COMBINE archives (SBML glycolysis BIOMD0000000176; a CellML hemodynamics model from the PMR), "latest versions … at the COMBINE GitHub repository" (combine-org/Annotations). The repository's `standardized/CellML` folder contained only a README on 2026-11-01; the archives were not retrieved. Which hemodynamics model was used is UNKNOWN.

Quotations

1. [Semantic annotations and their utility] "we make a distinction between semantic annotations and other types of metadata that do not indicate meaning, such as curatorial annotations that indicate model authorship, provenance annotations that indicate the origins of model components". → Q4 (semantic versus provenance).
2. [same] "One modeler may use a variable named 'X' to represent…, and another modeler may use 'X' to indicate…. In the absence of community-wide naming conventions, machine-accessible metadata is used to capture the meaning of model elements." → Q1.
3. [The Physiome Model Repository] "a model's variables must be linked to knowledge resource terms to capture the precise meaning of what a CellML model simulates. This presents challenges, as these variables represent concepts that can be very fine-grained …, and publicly available knowledge resources do not provide adequate coverage for such concepts." → Q1.
4. [The SemSim architecture and SemGen] "composite annotations: logical statements that link multiple knowledge resource terms to precisely define a model element." → Q1.
5. [same] "Depending on annotator preferences, synonymous terms from alternative knowledge resources could be used to create this composite annotation. For example, Uberon … could be used as an alternative to the FMA." → Q3 (two annotations of the same thing can differ by resource).
6. [Recommendations (i)] "We recommend using RDF … We recommend using the…URI format when referencing knowledge resource terms … We recommend the use of…qualifiers in annotation statements that define model elements." (identifiers.org URIs and BioModels.net qualifiers; names dropped by the PMC text) → Q3, Q4.
7. [Recommendations (ii)] "Externalizing annotations in a separate file allows a single model file to be referenced by multiple annotation files, allowing different research groups to describe the same modeling resource in different ways." → Q3.
8. [Recommendations (iv)] "the same biophysical concept represented in two different models might be annotated against different knowledge resource terms. This undermines the community's ability to compare and compose models in an automated fashion". → Q3.
9. [Recommendations (vi)] "to identify overly generic, overly specific and missing annotations; and to check that the annotations accurately capture the meaning of the model elements to which they are linked." → Q4 (semantic QC).
10. [Example semantic annotations] "To construct these pointers, we use the relative model file name for the URI base and the 'metaid' attribute on the annotated model element for the URI fragment." → Q4 (how a variable is referenced; provenance of the link).
11. [Discussion] "Applying the protocol, model-merging tools such as SemGen can recognize the biological commonalities between models and then use that information to compare the models' biological content and guide their assembly." → Q3.
12. [Discussion] "New tools that automate compliance-checking of annotations … could help flag errors, omissions and overgeneralizations." → Q4.

Author claim / our interpretation / independent confirmation

- Claim: RDF + identifiers.org URIs + BioModels.net qualifiers, stored separately, are the community basis; composite annotations are needed for fine-grained CellML variables; quality control and term mappings are open problems.
- Our reading: the paper draws the line the project needs for Q4: semantic annotation says what a variable means; provenance/curatorial metadata says where it came from; neither checks numbers. Recommendation (iv) concedes that identical concepts can carry different identifiers, so identifier equality is sufficient but not necessary for equivalence, and inequality is not evidence of difference.
- Independent confirmation: the identifiers.org form is what the SemSim-annotated Smith model uses (`http://identifiers.org/opb/OPB_00154`, S9), while our registry uses the native `http://bhi.washington.edu/OPB#` form; both resolved badly on 2026-11-01 (403 via BioPortal purl; 404 at bhi.washington.edu). See conflict C4.
- Limits/unknowns: the follow-on OMEX metadata specifications (S12/S13) are the normative form; "a full technical specification … is still under development" at the time of this paper.

## S7 W3C SHACL — Shapes Constraint Language

- W3C Recommendation 20 July 2017. This version https://www.w3.org/TR/2017/REC-shacl-20170720/; latest https://www.w3.org/TR/shacl/. Copyright © 2017 W3C (MIT, ERCIM, Keio, Beihang); W3C document licence. Namespace https://www.w3.org/ns/shacl (resolved HTTP 200).
- Access: specification text read in three windows (characters 0-100k, 30k-130k, 100k-200k, 200k-end).

Quotations (section numbers as in the Recommendation)

1. [Abstract] SHACL is "a language for validating RDF graphs against a set of conditions."
2. [§3.1] "A shapes graph is an RDF graph containing zero or more shapes"; [§3.2] "Any RDF graph can be a data graph."
3. [§2.1.2] "An RDF term that is validated against a shape using the triples from a data graph is called a focus node."
4. [§3.5] "A focus node conforms to a shape if and only if the set of result of the validation … is empty and no failure has been reported by it."
5. [§3.6.1] "The result of a validation process is an RDF graph with exactly one SHACL instance of sh:ValidationReport."; [§3.6.1.1] "The value of sh:conforms is true if and only if the validation did not produce any validation results".
6. [§4.1.1] "The condition specified by sh:class is that each value node is a SHACL instance of a given type."; [§4.1.2] sh:datatype: "The datatype of all value nodes."
7. [§4.2.1] "If the number of value nodes is less than $minCount, there is a validation result."; [§4.2.2] "If the number of value nodes is greater than $maxCount, there is a validation result."
8. [§4.5.1] sh:equals: "For each value node that does not exist as a value of the property $equals at the focus node," (a result is produced); [§4.5.2] sh:disjoint: "For each value node that also exists as a value of the property $disjoint at the focus node".
9. [§4.8.2] sh:hasValue: "If the RDF term $hasValue is not among the value nodes, there is a validation result."; [§4.8.3] sh:in: "For each value node that is not a member of $in, there is a validation result with the value node as sh:value."
10. [§4.8.1] sh:closed: "If $closed is true then there is a validation result for each triple that has a value node as its subject" (other than listed properties).
11. [§5] "SHACL-SPARQL supports a constraint component that can be used to express restrictions based on a SPARQL SELECT query."; [§5.3.1] "the SHACL-SPARQL processor pre-binds values for the variables"; `this` = "The focus node."
12. [§1.3] Core processors without SHACL-SPARQL support "ignore any SHACL-SPARQL constructs such as sh:sparql triples."

Our interpretation (role in this project): SHACL can state and check structural rules over the annotation graph, for example "every variable annotated with Fluid pressure must name exactly one bearer entity and one pressure reference", "a flow variable must have exactly one source and one sink participant", or "two variables asserted equivalent must have identical property, bearer, reference and temporal context". It reports conformance of the graph to those rules; it does not establish that the rules are physiologically right, and it cannot see numbers in CSV outputs. Conformance is "no validation results", so a rule that is never triggered because the data were never annotated passes vacuously unless `sh:minCount` is used. No SHACL file was written in this review.

[§4.2] prov:hadPrimarySource: "A primary source for a topic refers to something produced by some agent with direct experience and knowledge about the topic"; prov:wasQuotedFrom: "A quotation is the repeat of (some or all of) an entity, such as text or image,"; prov:wasRevisionOf: "A revision is a derivation for which the resulting entity is a revised version of some original."

Our interpretation (role in this project): PROV-O gives the vocabulary for the provenance half of Q4: which CellML file (entity, with hash) a run used, which solver activity generated which CSV, which agent (Hermes, OpenCOR 0.8.3, a person) is responsible, and that OPB master `wasRevisionOf` v1.07. `prov:alternateOf` versus `prov:specializationOf` is also the closest standard vocabulary for "two annotations describe the same thing from different aspects" without asserting identity. PROV-O records history; it does not validate that numbers are right or that a mapping is physiologically sound. No PROV graph was written in this review.
